# 설계 노트

이 문서는 sh-notice-mcp를 왜 이렇게 만들었는지, 실제 SH 사이트·공고문을 분석하며 알게 된 것과 테스트로 잡은 버그를 정리합니다. 사용법은 [README](../README.md)를 보세요.

### PDF와 판단
1. **모집공고문 PDF만 고른다** — 분양 공고는 위임장·개인정보 동의서·팸플릿·자금조달계획서가 함께 올라옵니다. 파일명에 `모집공고문/모집공고/공고문`이 있으면 점수를 주고, 서식·결과 파일 단어가 있으면 제외합니다. `[정정]` 공고문은 제외하지 않습니다(그게 읽어야 할 파일). 후보가 둘 이상이면 **추측하지 않고** `need_choice`로 사람에게 묻습니다.
2. **요약·판단은 Claude, 수집·검증·쓰기는 서버** — 서버는 PDF를 섹션으로 잘라 건넬 뿐 LLM을 호출하지 않습니다. 서버에 API 키·비용이 없고, 결정적인 부분만 테스트하면 됩니다.
3. **목차(CONTENTS) 기준으로 섹션 나누기** — 실제 제51차 장기전세 공고문(64쪽)을 분석해 보니 3쪽에 목차(`1. 공급일정 …… 9`, `<별표2> 소득 및 자산 … 54`)가 있고, 본문 장 제목은 `01 | 공급 일정`처럼 목차와 같은 쪽에 있습니다. 처음 짐작한 `Ⅰ. 제목` 형식이 아니었습니다. 그래서 목차를 먼저 찾아 자르고, 인쇄 쪽 번호와 PDF 쪽 번호가 다르면 `NN |` 제목 위치로 보정합니다. 목차 앞쪽(표지 일정표·입주자격 기준 요약·소득자산 요약)은 `표지·공고 요약` 섹션으로 묶어 가장 먼저 줍니다. 목차가 없으면 제목 패턴으로 나눕니다.
4. **맥락 절약, 단 자르지 않기** — 공고문을 통째로 주지 않고 핵심 섹션을 우선순위(요약 → 공급일정 → 신청자격 → 소득·자산)대로 12,000자까지 줍니다. 실제 공고문에서는 요약(p.1–8, 7.5K자) + 공급일정(p.9–11, 4K자)이 먼저 갑니다. 자격 조건이 반쯤 잘리면 오판할 수 있어서, 들어가지 않는 섹션은 자르지 않고 `read_next`로 알려 이어서 읽게 합니다.
5. **근거 인용** — 섹션마다 페이지 범위를 붙여서, 자격 판단 때 "p.12 소득기준 vs 내 소득"처럼 근거를 보여주게 합니다.
6. **개인정보는 로컬에만** — 내 조건은 `~/.sh-notice-mcp/profile.toml`에만 있습니다. 로컬 MCP(stdio)를 고른 이유 중 하나입니다. 주민번호 같은 식별정보는 받지 않습니다.

### 숫자는 서버가, 해석은 Claude가
- **가격표 직접 파싱** — 실제 고덕강일 3단지 공고문(136쪽, 앞 43쪽은 팸플릿)의 분양가표는 `동 호 주택형 평면유형 주택가격(천원) 계약금 잔금 발코니확장비(원)` 한 줄에 한 세대입니다. 서버가 이 행을 읽어 **대표 타입(청약 신청 단위, 49C1~C3 → 49C)별 평균·최저·최고 분양가와 발코니 확장비 합계**를 계산합니다. `계 = 계약금 + 잔금`, `계약금 ≈ 10%` 관계가 맞는 행만 받아 잘못 붙은 숫자를 거릅니다. 실제 공고문 전체에서 **1,305세대 전부 파싱, 오류 행 0개, 타입별 세대수가 공고문 p.51 공식 수치와 모두 일치**했습니다.
- **토지임대료와 보증금 전환** — "월 토지임대료의 최대 60%를 보증금으로, 100만원 단위" 규칙과 예시 이율을 공고문에서 읽어 계산합니다. 계산식은 **공고문 p.82 예시표(49㎡ 426,000원 → 보증금 1억 2,200만원, 월 171,830원)를 원 단위까지 재현**하는지 테스트합니다. 이율이 '확정 예정'인 예시값이면 그렇다고 표시합니다.
- **장기전세** — 단지명이 여러 줄에 걸친 표라 숫자 행(전세금·면적, 관계 검증)만 서버가 뽑고, 단지명 매칭은 행 앞 문맥을 보고 Claude가 합니다. 장기전세는 월 임대료가 없다고 명시합니다.
- **대출** — LTV·한도·만기·금리를 원문 문장과 쪽 번호로 돌려줍니다(예: p.44 "최대 5억원 한도(LTV 최대 80%, 만기 최장 40년, 고정금리 1.9~3.0%)").
- **같은 소제목 구분** — 분양 공고문은 `1. 청년 특별공급 ■ 신청자격`, `2. 신혼부부 특별공급 ■ 신청자격`처럼 소제목이 반복돼, 섹션 이름에 상위 제목을 붙입니다(`2. 신혼부부 특별공급 › 신청자격`).

### 내 조건
- **모름 ≠ 0** — 모르는 항목은 비워 둡니다. 예전엔 0이 기본값이라 '자녀 0명'과 '모름'을 구분할 수 없었습니다.
- **계산값 제공** — 나이, 혼인 개월 수, 신혼부부 7년 해당 여부와 끝나는 날, 서울 거주 연수를 서버가 계산해 줍니다(AI의 날짜 계산 실수 방지).
- **빠진 조건 먼저 묻기** — 공고문에 '부양가족', '무주택기간', '자동차', '생애최초', '2023.3.28 이후 출생' 같은 기준이 있는데 내 조건이 비어 있으면, 요약 전에 근거 문장과 함께 묻습니다.
- **말로 수정, 확인 후 저장** — 대화를 잘못 알아들어 조건이 바뀌면 이후 판단이 전부 틀어지므로, 캘린더 등록과 같은 Mac 확인 창을 거칩니다. 주석을 보존하며 값만 바꿉니다.

### 사람의 최종 확인
7. **확인 없는 쓰기 경로가 없다** — 예전의 `add_calendar_event`(바로 쓰기)를 없애고 `propose`(쓰기 없음) → `confirm`(사람 확인 후 쓰기) 두 단계로 바꿨습니다. 캘린더에 쓰는 도구는 `confirm_registration` 하나뿐입니다.
8. **확인은 서버가 직접 받는다** — Claude 앱의 도구 승인은 사용자가 '항상 허용'하면 사라지고, AI가 "사용자가 확인했다"고 말하는 건 확인이 아닙니다. macOS에서는 서버가 **Mac 기본 선택 창**을 띄워 사람이 체크한 일정만 씁니다(AI가 누를 수 없음). macOS가 아니면 MCP **elicitation**을 쓰는데, 사양상 클라이언트가 자동 응답할 수 있어 보장 수준이 낮다는 점을 문서화했습니다. 둘 다 불가하면 **등록하지 않습니다**.
9. **플랜은 한 번만, 1시간만** — 같은 확인으로 두 번 등록되지 않고, 오래된 플랜으로 등록되지 않습니다.
10. **날짜를 원문으로 검증한다 (grounding)** — 어떤 일정을 넣을지는 Claude가 고르지만, 날짜가 공고에 실제로 있는지는 서버가 확인합니다. 게시글 본문과 공고문 PDF 각 쪽에서 같은 날짜가 적힌 줄을 찾아 `근거: 공고문 p.9 「[1순위] 2026. 9. 14.(월) 10:00 ~ …」`처럼 붙이고, 못 찾으면 `원문 근거 없음`으로 거부합니다. 실제 공고에 쓰이는 표기(`2026. 9. 14.`, `’26.09.14.`, `~ 10.27.`처럼 연도를 생략한 범위 끝, 연말을 넘어가는 범위)를 모두 읽습니다. 날짜는 맞는데 시각이 다르거나, 근거 문장에 일정 이름의 단어가 없으면(다른 일정의 날짜를 붙인 경우) 경고하고 확인 창에 ⚠로 표시합니다. 근거는 캘린더 메모에도 남습니다.
11. **AI 입력을 믿지 않는다** — 제목·링크는 원문에서 다시 가져오고, 날짜는 pydantic으로 검증합니다(종료<시작, 60일 초과, 연도 범위, SH 외 링크 거부). 플랜 단계에서 지난 일정·이미 등록한 일정도 걸러 이유와 함께 돌려줍니다.
12. **cron은 알리기만** — 사람 확인이 필요한 흐름이라 자동 실행은 새 공고·읽을 PDF·일정 후보를 보고만 합니다. 터미널에서 등록하려면 `--review`로 y/n을 직접 답합니다.

### 크롤링·저장
13. **새 글 판단과 멱등성** — SQLite에 '본 글'과 '등록한 일정'을 따로 저장. 일정은 `공고 seq + 라벨 + 시작시각` 해시를 키로 써서 몇 번을 실행해도 한 번만 등록됩니다.
14. **첫 실행 기준선 / 실패 복구** — 첫 실행은 현재 글을 기준선으로만 저장. '봤다'와 '처리했다'를 분리해 도중에 죽어도 다음 실행에서 다시 처리합니다.
15. **오늘 이후 일정만** — 종료일이 오늘 이전이면 제외. 이미 시작했지만 안 끝난 기간(서류제출 등)은 포함합니다.
16. **사이트 배려** — 요청 간 1초 간격, 지수 백오프 재시도, 1페이지만 확인, PDF는 디스크에 캐시해 다시 받지 않음, 40MB 상한.
17. **도구 힌트·오류 전달** — `ToolAnnotations`(read_only/destructive/idempotent)로 도구 성격을 알리고, 예상된 오류는 `ToolError`로 이유를 돌려줘 AI가 고쳐서 재시도하게 합니다. 예상 못 한 예외는 숨깁니다.
18. **주입 방지** — AppleScript에 값을 문자열로 끼우지 않고 `argv`로 넘깁니다.

### 사이트 분석으로 알아낸 것
- 목록: '공고 및 공지 > 전체' 게시판(`m_241`)의 `list.do`에 **POST**. `multi_itm_seq`가 공지분류(1=주택분양, 2=주택임대), `itm_seq_1=1`이 '모집공고', `splyTy`가 임대 공급유형(03=장기전세, 07=행복주택 …), `srchTp=0`+`srchWord`가 제목 검색. 화면의 '공지분류' 드롭다운은 분류별 게시판 주소로 이동시키지만, 전체 게시판에 `multi_itm_seq`만 바꿔 보내도 같은 결과가 나와 한 곳에서 조회합니다.
- 모집공고 필터에도 '최종 청약 경쟁률', '당첨자 발표' 같은 후속 글이 섞여 나와 제목으로 거릅니다.
- 글 번호: `onclick="getDetailView('309467')"`에서 정규식으로 추출. 상세는 `view.do?seq=…` GET도 가능해 캘린더 메모에 원문 링크로 넣습니다.
- 첨부파일: 화면 링크가 아니라 페이지 스크립트의 `initParam.downList`(JSON)에 파일 번호·크기·이름이 있습니다. 다운로드는 `/main/com/file/innoFD.do?brdId=…&seq=…&fileTp=A&fileSeq=…`.
- 다운로드 서버는 **HEAD 요청에 401**을 돌려주지만 GET은 쿠키·리퍼러 없이 됩니다. 처음엔 인증이 필요한 줄 알았다가, 메서드 차이였음을 확인했습니다.

### 테스트가 잡아낸 버그

| 증상 | 원인 | 해결 |
|---|---|---|
| MCP로 첫 도구 호출부터 실패 | SDK가 동기 도구를 작업 스레드에서 실행, sqlite 연결은 만든 스레드에서만 사용 가능 | 작업마다 연결을 열고 닫음 |
| 첫 실행 때 게시판이 비어 있으면 다음 새 글이 사라짐 | '저장된 글이 있으면 초기화됨'으로 판단 | 초기화 시점을 별도 테이블에 기록 |
| 소제목('일반공급')이 사라짐 | `"" in "■□"`가 `True` | 집합 비교로 변경 |
| PDF의 `■ 공급호수: 1,381세대`가 섹션 제목이 됨 | 글머리표만 보고 제목 판단 | `항목: 값` 형태와 날짜가 든 줄은 제목에서 제외 |
| 내 조건 파일을 못 읽음 | TOML은 한글 키를 따옴표 없이 쓸 수 없음 | 영문 키 + 한글 주석 |
| 고덕강일 8·14단지 등 **주택 공고 4건이 '토지 분양'으로 제외될 뻔** | 제외 규칙 `택지`가 '공공**주택지**구'에 걸림 (실제 사이트 결과로 발견) | `(토지\|용지\|택지)\s*분양`처럼 '분양'과 붙을 때만 제외 + 회귀 테스트 |
| (설계 빈틈) AI가 날짜를 잘못 읽어도 형식만 맞으면 등록 후보가 됨 | 서버가 날짜의 '형식'만 검사 | 원문에서 날짜를 찾는 grounding 추가, 없으면 거부 |
| 분양 공고문(pypdf)에서 짝수 쪽마다 가짜 섹션, 분양가표가 2쪽씩 쪼개짐 | 쪽 아래 꼬리글 '44 \| 공고명'이 장 제목 패턴과 같음 (맥에서 실제 실행해 발견, 브라우저 추출에선 안 보였음) | 쪽의 20% 이상에서 반복되는 한글 줄을 머리글·꼬리글로 보고 제외. 숫자만 있는 분양가 행은 대상에서 빼서 보존 |
| '당첨자 선정방법'이 [공급일정]으로 분류됨 | '당첨자'라는 단어만 보고 일정으로 판단 | 일정·접수기간·신청기간만 일정 태그 |
| 실제 공고문이 섹션 1~2개로 뭉침 | 제목 형식을 `Ⅰ.`로 짐작함. 실제는 `01 \| 공급 일정` | 목차 기반 분할 + `NN \|` 제목 패턴 |

### 알려진 한계
- 자격 판단은 **참고용**입니다. 소득·자산 기준표는 복잡하고 예외가 많아, 최종 확인은 공고문 원문·청약홈에서 해야 합니다.
- 스캔(이미지)본 PDF·HWP 첨부는 읽지 못하고 그렇다고 알려줍니다(OCR 미지원).
- 표가 많은 페이지(예: 표지의 일정 인포그래픽)는 PDF 텍스트 추출 시 줄 순서가 섞일 수 있습니다. 그래서 일정은 게시글 본문(`extract_schedule`)과 교차 확인하게 했습니다.
- 게시판 1페이지(10개)만 확인합니다.

## 설계 Q&A

**MCP가 뭔가요?**
AI 앱(클라이언트)과 외부 도구(서버)를 잇는 표준 프로토콜입니다. 서버가 "이런 도구가 있다"를 알려주면 클라이언트의 모델이 필요할 때 도구를 호출합니다. 이 서버는 Claude 앱이 자식 프로세스로 실행하고 stdin/stdout으로 JSON-RPC를 주고받는 로컬(stdio) 방식입니다.

**왜 '서버'인가요?**
크기가 아니라 역할입니다. 요청을 받아 기능을 제공하는 쪽이 서버, 요청하는 쪽이 클라이언트입니다. 내 노트북에서 도는 작은 프로그램도 서버입니다.

**왜 로컬 MCP로 했나요?**
맥 캘린더 앱이 내 컴퓨터 안에 있어서 AppleScript로 접근하려면 같은 기기에서 돌아야 합니다. Google 캘린더를 쓴다면 원격 MCP로 배포하는 게 맞고, 백엔드를 인터페이스로 분리해 두어서 바꾸기 쉽습니다.

**LLM에게 날짜 추출을 다 맡기지 않은 이유는?**
SH 공고는 형식이 일정해서 규칙으로 대부분 잡히고, 규칙은 결정적이고 테스트 가능하고 비용이 없습니다. LLM은 예외 문장을 보완하는 역할이고, LLM이 넘긴 값도 같은 검증을 통과해야 등록됩니다.

**같은 일정이 두 번 들어가는 건 어떻게 막았나요?**
공고 번호 + 라벨 + 시작시각을 해시한 키를 DB에 저장하고 등록 전에 확인합니다. 그래서 cron이 돌든 AI가 같은 도구를 두 번 부르든 결과가 같습니다(멱등성).

**처음 실행하면 옛날 공고가 다 들어가지 않나요?**
첫 실행 때는 현재 글을 기준선으로 저장만 합니다. 이걸 '저장된 글이 있는지'로 판단했다가, 게시판이 비어 있던 경우 다음 새 글을 놓치는 버그를 테스트로 찾아서 초기화 시점을 따로 기록하도록 고쳤습니다.

**처리 중에 죽으면요?**
'본 글'과 '처리한 글'을 분리했습니다. 처리 완료 표시가 없는 글은 다음 실행 때 다시 처리됩니다. 일정 등록은 멱등이라 다시 처리해도 중복이 안 생깁니다.

**AI가 잘못된 날짜를 넣으려 하면?**
pydantic 모델에서 종료 < 시작, 60일 넘는 기간, 허용 범위 밖 연도, SH가 아닌 링크를 거부합니다. 그 이유를 ToolError로 돌려줘서 모델이 고쳐서 다시 시도할 수 있습니다.

**지난 일정은 어떻게 처리하나요?**
끝나는 날이 오늘 이후인 일정만 등록합니다. 시작일 기준이면 이미 시작한 서류제출 기간이 빠지기 때문에 종료일 기준으로 했습니다. 이 규칙을 MCP 도구가 아니라 서비스 계층의 등록 함수 한 곳에 둬서, cron 경로든 AI가 직접 날짜를 넘기는 경로든 우회할 수 없습니다. 테스트에서는 '오늘'을 주입해서 날짜가 지나도 테스트가 깨지지 않게 했습니다.

**보안 측면에서 신경 쓴 점은?**
① 삭제·수정 도구 미제공 ② 제목·링크는 원문에서 재조회 (본문에 '이 링크를 넣어라' 같은 문장이 있어도 반영 안 됨) ③ AppleScript에 값을 문자열로 끼우지 않고 argv로 전달해 주입 방지 ④ 예상 못 한 예외의 상세는 서버 로그에만.

**사이트 구조가 바뀌면?**
파서가 테이블을 못 찾으면 명확한 ScrapeError를 냅니다. 실제 HTML을 줄인 fixture로 테스트하고 있어서 구조 변경을 빨리 알 수 있습니다.

**일정 등록은 무엇을 근거로 하나요? AI가 날짜를 잘못 읽으면요?**
역할을 나눴습니다. 어떤 일정이 나에게 해당하는지는 Claude가 공고문과 내 조건을 보고 고르지만, 그 날짜가 공고에 실제로 있는지는 서버가 확인합니다. 게시글 본문과 공고문 PDF 각 쪽에서 같은 날짜가 적힌 줄을 찾아 출처·문장을 근거로 붙이고, 못 찾으면 거부합니다. 9월 14일을 15일로 잘못 읽거나 없는 날짜를 만들면 여기서 걸립니다. 날짜는 있는데 시각이 다르거나, 근거 문장이 일정 이름과 관계없으면 경고하고 확인 창에 ⚠로 보여줍니다. 처음 만들 때는 서버가 날짜 '형식'만 검사하고 있었는데, 그게 빈틈이라는 걸 깨닫고 추가한 기능입니다. LLM의 출력을 원문에 대조하는 grounding입니다.

**분양가 평균 같은 숫자는 AI가 계산하나요?**
아니요. 숫자는 서버가 공고문 가격표를 직접 파싱해 계산합니다. 1,305세대 분양가를 AI가 읽고 평균을 내면 빠뜨리거나 틀리기 쉽습니다. 행마다 '계 = 계약금 + 잔금' 관계를 검사해 잘못 붙은 숫자를 거르고, 실제 공고문에서 1,305세대가 오류 0개로 파싱되고 타입별 세대수가 공고문의 공식 표와 모두 일치하는 걸 확인했습니다. 토지임대료 보증금 전환 계산식은 공고문에 실린 예시표를 원 단위까지 재현하는지 테스트합니다. AI는 이 숫자를 표로 옮기고, 자격을 해석하는 일만 합니다.

**요약하기 전에 왜 질문부터 하나요?**
공고마다 판단 기준이 다릅니다. 어떤 공고는 자동차가액을, 어떤 공고는 부양가족 수나 2023년 3월 28일 이후 출생 자녀를 봅니다. 공고문에 그 기준이 있는데 내 조건이 비어 있으면, 추측해서 '해당'이라고 하는 대신 근거 문장과 함께 먼저 묻게 했습니다. 프로필도 '모름'과 '0'을 구분하도록 바꿨습니다.

**PDF가 여러 개면 어떻게 골라요?**
파일명 점수입니다. '모집공고문/모집공고/공고문'이 있으면 가산하고, 위임장·동의서·팸플릿·계획서·명단 같은 서식은 제외합니다. '[정정]'은 제외하지 않습니다. 정정 공고에서는 그게 읽어야 할 파일이기 때문입니다. 후보가 둘 이상이면 고르지 않고 사람에게 묻습니다. 잘못된 문서를 근거로 자격을 판단하는 게 제일 위험하니까요.

**왜 서버에서 LLM을 부르지 않았나요?**
MCP에서는 클라이언트(Claude)가 이미 모델입니다. 서버가 또 LLM을 부르면 키·비용·프롬프트 관리가 서버로 넘어오고 테스트도 어려워집니다. 서버는 결정적인 일(수집·선택·자르기·검증·쓰기)만 하고, 해석은 클라이언트에 맡겼습니다.

**공고문이 80쪽이면요?**
통째로 주면 대화 맥락을 다 써버립니다. 목차와 핵심 섹션(일정·자격·소득자산·순위)만 먼저 주고, 나머지는 섹션 단위로 필요할 때 읽게 했습니다. 섹션마다 페이지가 붙어 있어서 판단 근거를 페이지로 인용할 수 있습니다.

**'사람 확인'을 어떻게 보장하나요?**
세 겹입니다. ① 쓰기 도구가 confirm_registration 하나뿐이고, 그 전 단계인 propose는 아무것도 쓰지 않습니다. ② confirm 안에서 서버가 Mac 기본 선택 창을 직접 띄웁니다. Claude는 그 창을 누를 수 없고, 체크한 일정만 씁니다. ③ 확인 수단이 없는 환경이면 등록을 거부합니다. MCP elicitation도 지원하지만, 사양상 클라이언트가 자동 응답할 수 있어서 Mac에서는 기본값으로 쓰지 않았습니다. Claude 앱의 도구 승인은 '항상 허용'을 누르면 사라지기 때문에 그것만 믿지 않았습니다.

**개인정보는요?**
내 조건은 로컬 파일 하나에만 있고, 서버는 외부로 보내지 않습니다. 다만 Claude가 판단하려면 대화 중에 읽기 때문에, 판단에 필요한 항목만 받고 주민번호 같은 식별정보는 받지 않습니다. 원격이 아니라 로컬 MCP를 고른 이유 중 하나입니다.

**자격 판단이 틀리면요?**
참고용이라고 명시하고, 근거 페이지와 내 조건 항목을 짝지어 보여주게 했습니다. 정보가 없으면 추측하지 말고 묻게 프롬프트를 설계했습니다. 다음 단계로 소득·자산 기준표를 구조화해 1차 판정은 규칙으로 하고 LLM은 설명만 맡기려 합니다.

**실제 데이터에서 배운 것은?**
세 가지입니다. ① 공고문 제목 형식을 `Ⅰ. 제목`으로 짐작하고 짰는데, 실제 64쪽 공고문을 열어 보니 목차가 있고 장 제목은 `01 | 공급 일정`이었습니다. 짐작 대신 문서가 이미 가진 구조(목차)를 쓰도록 바꿨습니다. ② 토지 분양을 거르려고 '택지'를 넣었더니 '공공주택지구'가 걸려서 진짜 주택 공고 4건이 빠질 뻔했습니다. 규칙을 만들면 실제 데이터 전체에 돌려 오탐을 확인해야 한다는 걸 배웠고, 그 사례를 회귀 테스트로 남겼습니다. ③ 사이트 검색이 띄어쓰기를 구분해서, 검색어 하나로는 공고 3건이 빠졌습니다. 검색어 세 개를 OR로 합쳤습니다.

**개발 환경과 실제 환경이 달라서 생긴 문제는?**
PDF 구조는 브라우저의 pdf.js로 분석했는데, 프로젝트는 pypdf를 씁니다. 맥북에서 실제로 돌려 보니 pypdf는 쪽 아래 꼬리글을 '44 | 공고명' 형태로 뽑아서, 장 제목 패턴('01 | 공급 일정')과 똑같아 보였습니다. 그래서 반복되는 머리글·꼬리글을 찾아 빼는 전처리를 넣었는데, 처음 생각한 '숫자를 지우고 비교' 방식대로 하면 분양가 행도 모두 같은 줄로 보여 지워질 뻔했습니다. 한글이 있는 줄만 대상으로 해서 해결했고, 두 경우 모두 테스트로 남겼습니다. 같은 문서라도 추출 도구에 따라 결과가 달라서, 최종 검증은 실제 실행 환경에서 해야 한다는 걸 배웠습니다.

**테스트는 통과했는데 실제로 틀린 적은?**
'최근 뜬 공고' 기능을 실제 앱에서 돌려 보니 제51차 장기전세의 접수 기간이 9/16~9/17로 나왔습니다. 실제로는 9/14~9/17이었습니다. 원인은 HTML이었습니다. 테스트용 HTML은 `<p>` 한 줄이었지만, 실제 SH 본문은 한 문단이 글자 단위 `<span>`으로 쪼개져 있었습니다. 저는 태그마다 줄을 바꿔 읽었기 때문에 '[1순위] 2026. 9. 14.'가 다섯 줄로 흩어져 1순위 접수일을 놓쳤습니다. 그래서 블록 태그(p·div·li)와 `<br>`에서만 줄을 바꾸도록 고쳤습니다. 실제 본문을 그대로 재현한 데이터로 회귀 테스트를 만들어, 고치기 전에 같은 오답이 나오는 것부터 확인했습니다. 테스트 데이터는 실제 데이터를 그대로 떠 와야 한다는 걸 배웠습니다.

**삽질한 것은?**
첨부파일 다운로드 주소에 HEAD를 보냈더니 401이 와서 인증이 필요한 줄 알았는데, GET은 쿠키 없이 됐습니다. 서버가 HEAD만 막은 거였어요. 결론을 내기 전에 조건을 하나씩 바꿔 확인하는 게 중요하다는 걸 배웠습니다.

**MCP와 AI 에이전트는 어떻게 다른가요?**
MCP 서버는 **도구**이고, 에이전트는 그 도구를 **언제 어떤 순서로 쓸지 정하는 쪽**입니다. 에이전트 루프는 마법이 아니라 반복입니다: ① 도구 목록을 LLM에 주고 ② LLM이 tool_use로 도구와 인자를 고르면 ③ 내 코드가 MCP 서버에 실제로 호출하고 ④ 결과를 돌려주고, LLM이 더 부를 게 없다고 할 때까지 반복합니다. 이걸 SDK 없이 `agent.py`에 150줄로 직접 구현했고, 실행하면 `[3] Claude → get_housing_costs(...)`처럼 단계가 찍힙니다. 같은 MCP 서버를 비개발자는 Claude 앱에서 말로, 개발자는 코드로, 그리고 매일 아침 스케줄로 **스스로** 쓰게 했습니다.

**에이전트가 혼자 돌면 위험하지 않나요?**
에이전트를 믿는 대신 **믿지 않아도 되게** 설계했습니다. ① 새 공고 확인은 AI 없이 코드로 하고, 없으면 AI를 아예 부르지 않습니다(비용 0원, 불필요한 데이터 전송 없음). ② 혼자 도는 모드에는 '내 조건 수정' 도구를 아예 보여주지 않습니다(허용 목록). ③ 최대 25단계·토큰 예산으로 폭주를 막습니다. ④ 캘린더 쓰기는 서버 안에서 Mac 확인 창을 띄우므로 에이전트가 대신 누를 수 없습니다. ⑤ API 키는 코드·설정 파일이 아니라 macOS 키체인에 둡니다. ⑥ 내 조건 파일은 내 컴퓨터에만 있습니다. 안전장치가 프롬프트가 아니라 **서버 코드**에 있어서, 어떤 에이전트를 붙여도 똑같이 지켜집니다.

**에이전트를 어떻게 테스트했나요?**
LLM 자리에 '정해진 순서로 도구를 부르는 가짜 Claude'를 넣고, MCP 서버는 **진짜 하위 프로세스**로 띄워 테스트합니다. 그래서 루프·허용 목록·단계 제한·'새 공고 없으면 AI 안 부름'을 네트워크와 비용 없이 결정적으로 검증합니다.
